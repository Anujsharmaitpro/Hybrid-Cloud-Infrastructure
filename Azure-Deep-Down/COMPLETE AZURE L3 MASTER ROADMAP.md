# MODULE 1 — AZURE ARCHITECTURE (Parts 1–3)

## 1.1 CONCEPT

Azure is not a single platform — it is a **hierarchical, multi-tenant cloud infrastructure** organized in concentric layers of governance, identity, networking, compute, and data. Every resource you interact with sits somewhere inside this hierarchy, and understanding *where* and *why* is the foundation of L3 operational competence.

At its core, Azure separates:
- **Who you are** (Microsoft Entra ID / identity plane)
- **What you can do** (RBAC / authorization plane)
- **What you govern** (Policy, Locks, Tags / governance plane)
- **Where your resources live** (Regions, Subscriptions, Resource Groups / location plane)
- **How your resources communicate** (Networking / data plane)

An L3 engineer who understands this hierarchy can:
- Trace a failure across multiple layers
- Identify whether an issue is identity, governance, network, or compute
- Explain to architects, security teams, and executives why things are structured the way they are
- Design resilient, auditable, and operationally manageable environments

---

## 1.2 ARCHITECTURE

The Azure hierarchy from broadest to most specific:

```
Azure Tenant (Microsoft Entra Tenant)
  └── Microsoft Entra ID (Directory)
        └── Management Groups (Optional — governance grouping)
              └── Subscriptions (Billing + access boundary)
                    └── Resource Groups (Logical container)
                          └── Azure Resources (VMs, Storage, VNets, etc.)
```

**Critical understanding:** These are NOT the same thing. A "tenant" in Azure has two distinct meanings:
1. The **Azure AD tenant** (now Microsoft Entra tenant) — the identity/auth boundary
2. The **Azure subscription tenant** — the billing and management boundary

They share a name but are different objects. An enterprise may have ONE Entra tenant with MULTIPLE subscriptions, or multiple Entra tenants federated together.

---

## 1.3 COMPONENTS (Deep Dive)

### 1.3.1 TENANT (Azure / Microsoft Entra Tenant)

**What it is:** The top-level trust boundary in Microsoft Entra ID. Every Azure subscription belongs to exactly one Microsoft Entra tenant.

**Why it exists:** It defines:
- A shared directory for identity
- A trust relationship between Microsoft and your organization
- The boundary for authentication, authorization, and directory services
- The root of trust for all identities (users, groups, service principals, managed identities)

**Key properties:**
- **Tenant ID** (Directory ID) — a GUID that uniquely identifies the Entra tenant. This is the "who are you" identifier when authenticating.
- **Default domain** — initially `onmicrosoft.com`, can be replaced with custom domains.
- **Capabilities:** Can be delegated to sub-organizations using **Entra ID B2B collaboration** (guest access) or **Entra ID B2C** (customer identities), though these are separate tenant models.

**How it communicates:** Every authentication request goes to the tenant's authority endpoint:
`https://login.microsoftonline.com/{tenant-id}`

**What depends on it:** EVERYTHING. Without the tenant, no identity, no RBAC, no resource access, no managed identity, no service principal.

**What it depends on:** Microsoft's global infrastructure, DNS for the Microsoft Entra endpoints, and the root Domain Name System resolution.

**Production reality:** In a large enterprise, the tenant is often shared across multiple business units but segmented via:
- Administrative units
- Conditional Access policies targeting specific groups
- Privileged Identity Management (PIM) for role elevation
- B2B guest access for partner/external collaboration

---

### 1.3.2 Microsoft Entra ID (Directory)

**What it is:** The directory service that lives inside the tenant. It is the successor to Azure Active Directory (Azure AD) — the name was changed in 2023.

**Why it exists:** It provides:
- Directory objects (users, groups, devices, service principals)
- Authentication and authorization services
- Directory replication across global datacenters
- Domain name management
- Certificate and key management (via Entra ID PKI)

**Key properties:**
- **Directory ID** = Tenant ID (same GUID, different name depending on context)
- **Domains:** Can have multiple verified domains (e.g., `contoso.com`, `contoso.onmicrosoft.com`)
- **Replication:** Internally replicates across global datacenters using multi-master replication (similar to AD DS conceptually, but different technology)

**Legacy vs Current:**
- **Legacy:** "Azure Active Directory" branding, "Azure AD" in all tooling and cmdlets
- **Current:** "Microsoft Entra ID", "Microsoft Entra" branding (as of March 2023). All Azure AD PowerShell cmdlets still work but are being transitioned. Newer docs use "Microsoft Entra."

**L3 Impact:** When troubleshooting sign-in issues, you are always troubleshooting within the context of the Entra ID directory. The tenant is the boundary; the directory is the operational view.

---

### 1.3.3 MANAGEMENT GROUPS

**What it is:** A hierarchy level between subscriptions and the tenant. Used to organize subscriptions into a governance tree.

**Why it exists:** Enterprises with 50+ subscriptions need a way to:
- Apply Azure Policy and RBAC at a higher scope than a single subscription
- Inherit governance (tags, policy, RBAC) to child subscriptions
- Organize subscriptions by business unit, application, environment (dev/test/prod), cost center, etc.

**Key properties:**
- Can have **up to 6 levels** in the hierarchy (including root)
- Each subscription can have only ONE parent management group
- Policy and RBAC assigned at a management group scope cascade down

**How it communicates:** Management Groups are a meta-layer — they don't have resources themselves. They communicate through inheritance: assignments at a parent MG propagate down to child MGs and subscriptions.

**What depends on it:** Azure Policy assignments, RBAC role assignments, and resource organization in large environments.

**What depends on it (downstream):** Subscriptions within the management group inherit all governance.

**Critical rule:** A subscription can be moved between management groups (with approval), but it cannot be moved between tenants. This is a fundamental enterprise architecture constraint.

---

### 1.3.4 SUBSCRIPTION

**What it is:** The fundamental billing and access management boundary in Azure.

**Why it exists:**
- Billing: Every resource in Azure is associated with a subscription for cost tracking
- Access control: RBAC role assignments can be made at subscription scope
- Resource organization: Subscriptions contain resource groups
- Security boundary: By default, resources in one subscription cannot access resources in another subscription (though this can be configured)

**Key properties:**
- **Subscription ID** — GUID uniquely identifying the subscription
- **Subscription Name** — friendly name
- **Subscription Tenant ID** — which Entra tenant the subscription belongs to (immutable once created)
- **Billing Account** — the enterprise agreement, MCA, or pay-as-you-go billing relationship
- **Enrollment** — the payment/billing relationship

**Legacy vs Current:**
- **Legacy:** In older Azure documentation, subscriptions were sometimes described as the primary organizational unit. In practice, management groups are now the recommended governance layer above subscriptions.
- **Current:** Microsoft recommends: Management Groups → Subscriptions → Resource Groups → Resources

**How it communicates:** A subscription is a container that communicates with ARM for deployment, with Entra ID for identity, and with resource providers for resource operations.

**What depends on it:** Resource Groups (must live inside a subscription), RBAC assignments at subscription scope, Policy assignments at subscription scope.

**What it depends on:** The Entra tenant (a subscription belongs to exactly one tenant).

**Production reality:** Enterprise practice is to NOT put all production workloads in one subscription. Common patterns:
- Separate subscriptions per environment (Dev/Test/UAT/Prod)
- Separate subscriptions per business unit
- Separate subscriptions for shared services
- Sandbox subscriptions for experimentation

---

### 1.3.5 RESOURCE GROUP

**What it is:** A logical container that holds Azure resources. It is NOT a security boundary and NOT a networking boundary.

**Why it exists:**
- Organize related resources (e.g., all resources for one application)
- Define a scope for RBAC (though this is discouraged at RG level in favor of resource-level or higher scopes)
- Define a scope for lifecycle management (delete all resources in the group at once)
- Deployment context for ARM/Bicep templates
- Metadata location (the RG location is where the metadata is stored, NOT where data resides)

**Key properties:**
- **Location** — the region where the RG metadata is stored. This does NOT determine where resources' data lives. A VM in a West US resource group can have disks in East US.
- **Name** — within a subscription, RG names must be unique
- **Tags** — can be applied at RG level and inherited

**Common misconception:** "The resource group location determines where data is stored." WRONG. The resource group location is a **metadata location**. A VM's OS disk can be in a different region. A storage account's data can be in a different region than its resource group. The resource group location determines where Azure stores the metadata about the resource group and its resources.

**How it communicates:** It serves as a deployment scope for ARM/Bicep. It groups resources logically. It has no network significance.

**What depends on it:** Individual resources (must belong to exactly one RG).

**What it depends on:** A subscription.

---

### 1.3.6 AZURE RESOURCES

**What it is:** Any entity managed by Azure — VMs, storage accounts, VNets, NICs, databases, etc.

**Key properties:**
- **Resource Name** — unique within its resource group
- **Resource Type** — defined by the resource provider (e.g., Microsoft.Compute/virtualMachines)
- **Resource ID** — globally unique identifier: `/subscriptions/{sub}/resourceGroups/{rg}/providers/{provider}/{type}/{name}`
- **Location** — where the resource physically resides (for regional resources)
- **Kind/Sku** — variant of the resource type
- **Tags** — for organization and cost tracking

**How it communicates:** Resources communicate via:
- Network interfaces and VNets (networking)
- Managed identities and service principals (authentication)
- Resource provider APIs (management plane)

**What depends on it:** Nothing (resources are leaves in the hierarchy).

**What it depends on:** Resource Group, Subscription, and underlying infrastructure (region, capacity).

---

### 1.3.7 RESOURCE PROVIDER

**What it is:** An Azure service that exposes resources through the Azure Resource Manager. Each resource type is registered with a resource provider.

**Examples:**
| Resource Provider | Resources |
|---|---|
| Microsoft.Compute | VMs, VM Scale Sets, Disk |
| Microsoft.Network | VNet, NIC, NSG, Load Balancer, VPN Gateway |
| Microsoft.Storage | Storage Accounts, Blob, File |
| Microsoft.KeyVault | Key Vault |
| Microsoft.Web | App Service |
| Microsoft.ContainerService | AKS, ACR |
| Microsoft.Authorization | Role Definitions, Policy |

**Why it exists:** Each Azure service registers a resource provider so ARM knows how to create, read, update, delete, and manage its resources.

**Registration:** Resource providers must be **registered** in a subscription before resources of that type can be deployed. If a provider is not registered, deployments fail with errors like:
> "The subscription is not registered to use resource provider 'Microsoft.Compute'."

**Registration state:**
- **Registered** — can create/manage resources
- **NotRegistered** — cannot create/manage resources (but existing ones may still work)
- **Unregistered** — all operations blocked

**Important:** For some providers (e.g., Microsoft.Compute), registration is automatic. For others, manual registration is required. This is a common L3 troubleshooting step when a new subscription is created.

**How it communicates:** Through ARM. Every CRUD operation on a resource goes through ARM → Resource Provider → Resource.

**L3 troubleshooting:** Before investigating why a deployment fails, check:
1. Is the resource provider registered?
2. Is there an RBAC permission issue?
3. Is there a policy denial?
4. Is there a quota issue?

---

### 1.3.8 AZURE RESOURCE MANAGER (ARM)

**What it is:** The central management layer for all Azure resources. It is the **control plane** for Azure.

**Why it exists:** ARM provides:
- A unified management layer for all resources
- Authentication and authorization via Entra ID
- Resource deployment (ARM templates, Bicep)
- Resource lifecycle management (create, update, delete, read)
- RBAC enforcement
- Policy enforcement
- Lock enforcement
- Tag management
- Dependency tracking during deployments
- Audit logging (Activity Log)

**Key distinction — ARM is NOT the data plane.** ARM handles management operations. When you access data in a storage account, that goes through the storage service's data plane endpoint (`https://{account}.blob.core.windows.net`), not through ARM.

**Deployment flow (what happens during a deployment):**
1. User/Service sends deployment request → Entra ID authenticates
2. ARM checks RBAC (does the principal have write permissions at the deployment scope?)
3. ARM evaluates Azure Policy (would any policy deny this deployment?)
4. ARM resolves dependencies between resources in the template
5. ARM validates the template/Bicep (syntax, parameters, references)
6. ARM sends resource creation requests to each resource provider
7. Resource providers create/manage resources in their respective control planes
8. ARM reports deployment status (success/failure)
9. If failure, ARM provides error details and (depending on mode) may roll back

**Deployment modes:**
- **Incremental (default)** — creates new resources, updates existing, does NOT delete resources not in the template
- **Complete** — creates new, updates existing, DELETES resources that exist but are not in the template (dangerous)
- **What-if** — shows what would happen without making changes (dry run)

**Key concept:** ARM is idempotent. Running the same deployment multiple times produces the same result.

---

### 1.3.9 REGIONS

**What it is:** A geographic area where Azure operates. Each region has one or more data centers.

**Key concepts:**
- **Azure Region** — e.g., "East US", "West Europe". A set of data centers in a geographic area.
- **Region Pair** — two Azure regions paired for DR purposes (e.g., East US ↔ West US). They are in separate fault domains and typically within 100–300 miles of each other (for replication latency).
- **Geographic Region** — broader geographic area (e.g., "Americas") used for compliance/sovereignty
- **Sovereign Regions** — for government compliance (e.g., Azure Government, Azure China)

**Availability Zones vs Regions:**
- **Region** — a single geographic area (e.g., East US)
- **Availability Zone** — a physically separate data center WITHIN a region (an Availability Zone is not the same as a region)
- **Region pairs** — for cross-region DR

**L3 Impact:** The region you choose affects:
- Latency to users
- Available services and SKUs
- Compliance/sovereignty requirements
- Pricing (data transfer costs between regions)
- Replication capabilities (GRS requires paired regions)
- VM availability and quotas

---

### 1.3.10 AVAILABILITY ZONES

**What it is:** Physically separate data centers within a single Azure region. Each zone has independent power, cooling, and networking.

**Key properties:**
- A region may have 1, 2, or 3 zones
- Not all services are zone-aware
- Zone-redundant resources replicate across zones automatically (e.g., ZRS storage, zone-redundant App Gateway)
- You can explicitly deploy zonal resources (e.g., VM in Zone 1, Zone 2, Zone 3)

**Not a zone:** An Availability Zone is NOT the same as a region. "East US" is a region. "Zone 1" within East US is an availability zone.

---

### 1.3.11 REGION PAIRS

**What it is:** Two Azure regions that are paired together for disaster recovery and replication purposes.

**Key properties:**
- Paired regions are typically within 100–300 miles
- They are in separate fault domains (so a hurricane/flood doesn't take out both)
- They have low replication latency (typically under 15 minutes)
- Used for GRS, RA-GRS, GZRS, RA-GZRS replication
- If one region goes down, the other can be used for failover

**Production example:** East US ↔ West US 2. If East US has a major outage, GRS-replicated storage in West US 2 can be accessed.

---

### 1.3.12 GLOBAL vs REGIONAL SERVICES

**What it is:** Some Azure services are global (not tied to a region) and some are regional.

**Global services:**
- Microsoft Entra ID (Azure AD)
- Azure Policy (global policy evaluation)
- Azure RBAC (directory-level role assignments)
- Azure Monitor (some components)
- Key Vault (global, but data is region-specific)
- Azure Front Door (global routing)
- Traffic Manager (DNS-based global routing)

**Regional services:**
- VMs, Storage, VNets, NSGs (all tied to a region)
- Azure SQL, Cosmos DB (region for data residency)
- Most compute and networking resources

**Why it matters:** When you deploy a global service, you don't specify a region. When you deploy a regional service, you MUST specify a region. Some global services have a "replication region" for data (e.g., Key Vault certificates can be stored in a specific region even though the service is global).

---

### 1.3.13 RESOURCE LOCATIONS vs METADATA LOCATIONS

**Critical distinction:**

- **Resource Location** — where the resource's data physically resides (e.g., a VM in "East US" has its compute and storage data in East US)
- **Metadata Location** — where the management metadata (resource group location, ARM deployment records) resides. This is where the RG is located.

**Example of confusion:**
- You create a Resource Group in "West US"
- You deploy a VM in "East US" inside that RG
- The VM's OS disk is in "East US"
- The Resource Group metadata is in "West US"

The RG location (West US) does NOT affect where the VM or its disks are. The VM location (East US) DOES determine where compute happens.

**Production impact:** When customers ask "where is my data?" — look at the resource's location property, NOT the resource group's location.

---

### 1.3.14 RESOURCE IDs

**What it is:** The globally unique identifier for every Azure resource.

**Format:**
```
/subscriptions/{subscription-id}/resourceGroups/{resource-group-name}/providers/{resource-provider-namespace}/{resource-type}/{resource-name}
```

**Example:**
```
/subscriptions/12345abc-6789-0123-4567-89abcdef0123/resourceGroups/myRG/providers/Microsoft.Compute/virtualMachines/myVM
```

**Key properties:**
- Immutable — once created, the resource ID does not change (even if you move the resource between RGs or subscriptions)
- Globally unique — no two resources in the world can have the same ID
- Contains the full hierarchy path

**Resource ID vs Resource Name:**
- **Resource Name** — unique within its resource group (e.g., "myVM")
- **Resource ID** — globally unique (contains subscription, RG, provider, type, name)

**Why it matters:**
- All API calls use resource IDs
- RBAC role assignments reference resource IDs as scope
- Policy assignments reference resource IDs as scope
- All references in templates use resource IDs
- All diagnostic settings and alert scopes use resource IDs

---

### 1.3.15 TAGS

**What it is:** Key-value pairs attached to resources for organization and categorization.

**Key properties:**
- Can be added to any resource
- Can be added at RG level (propagates to resources in the RG)
- NOT inherited by resources created inside the RG (must be applied explicitly or via policy)
- Used for cost allocation, organizational purposes, and automation
- Maximum 50 tags per resource, each key up to 512 chars, value up to 256 chars
- Tag names are case-insensitive

**Common enterprise tags:**
- `Environment` = Prod/Dev/Test/UAT
- `Application` = AppName
- `Owner` = Team/Email
- `CostCenter` = CC-1234
- `DataClassification` = Public/Internal/Confidential

**Governance role:** Tags are used by Cost Management for chargeback/showback. They are also required by many enterprise governance policies ("Require tag `Environment` on all resources").

**Important:** Tags do NOT affect resource functionality. They are metadata. However, policies can REQUIRE tags, and then they DO affect whether you can deploy resources.

---

### 1.3.16 LOCKS

**What it is:** A mechanism to prevent accidental deletion or modification of resources.

**Types:**
- **CanNotDelete** — prevents deletion of the resource (modification still allowed)
- **ReadOnly** — prevents both deletion and modification

**Lock inheritance:** Locks at a parent scope (e.g., subscription) apply to all resources within that scope. A lock at the subscription level means NO resource in that subscription can be deleted. Locks are inherited from:
- Management Group → Subscription → Resource Group → Resource

More restrictive locks at a child level do NOT override less restrictive locks at a parent level. If a subscription has CanNotDelete, you cannot delete individual resources within it even if the resource itself has no lock.

**Who can create/delete locks:** The lock is an ARM-level operation. Even if you have "Contributor" access to a resource, you need "Microsoft.Authorization/*" or "Microsoft.Authorization/locks/*" permission to manage locks. Typically, Owners and User Access Administrators can manage locks.

**Production reality:** Always put CanNotDelete locks on production resources. Always lock Resource Groups containing production resources. This is a primary defense against accidental deletion.

---

### 1.3.17 QUOTAS / LIMITS

**What it is:** Constraints on resource usage within a subscription, region, or resource provider.

**Types:**
- **Subscription quotas** — max number of resources per type per subscription
- **Regional quotas** — vCPU limits per region per subscription
- **Resource limits** — e.g., max disks per VM, max NICs per VM
- **API rate limits** — throttling on ARM API calls

**Key quotas:**
- vCPU quota (default 20 per region — easily exceeded in enterprise environments)
- Network interfaces per subscription
- Public IPs per subscription
- Storage accounts per subscription
- Load balancer rules per load balancer

**When quotas are exceeded:** Deployments fail with "Quota exceeded" errors. The resource is NOT created. You must request a quota increase via Azure Support.

**Quota vs Policy vs RBAC:**
- **Quota exceeded** → resource cannot be created (capacity limit)
- **Policy denied** → resource cannot be created (governance rule)
- **RBAC denied** → user cannot perform the action (permission issue)

All three produce a "deployment failed" error but for completely different reasons. L3 troubleshooting MUST distinguish between these.

---

### 1.3.18 ARM DEPLOYMENT MODEL

**What it is:** The way ARM manages resources through templates and APIs.

**Two deployment models (historical):**
- **Classic (Service Management / ASM)** — the original Azure deployment model (retired). Used `*.azurewebsites.net` style endpoints. Legacy.
- **Resource Manager (ARM / ARM)** — the current deployment model. All new resources use this.

**Current state:** All Azure resources are deployed through ARM. The "classic" model is fully deprecated. If you encounter "ASM" or "Classic" in documentation, it is legacy and should not be used.

**Modern IaC:**
- **ARM Templates** (JSON) — the native ARM deployment format. Mature, fully supported.
- **Bicep** — a domain-specific language that compiles to ARM JSON. More readable, more maintainable, recommended by Microsoft for all new deployments.
- **Terraform** — third-party IaC tool with Azure provider. Stateful (maintains external state file). Awareness is required; state management is a critical operational concern.

## 1.4 COMPONENTS — HOW THEY CONNECT

```
User/Admin
    │
    ▼
Microsoft Entra ID (Tenant/Directory)
    │ (authenticates who you are)
    ▼
Azure Resource Manager (Control Plane)
    │ (checks RBAC, Policy, Locks)
    ▼
Resource Provider (e.g., Microsoft.Compute)
    │ (creates/manages the actual resource)
    ▼
Azure Resource (e.g., Virtual Machine)
    │ (lives in a Resource Group, in a Subscription)
    ▼
Data Plane (e.g., VM's OS, Storage data path)
    │
    ▼
End User/Application Traffic
```

**The complete chain for a deployment:**
1. You sign in → Entra ID authenticates → issues token
2. You run `az deployment create` → ARM receives request with your token
3. ARM validates token → checks RBAC (can this identity deploy at this scope?)
4. ARM evaluates Policy (would any policy deny?)
5. ARM checks Locks (is anything locked?)
6. ARM parses template/Bicep → resolves dependencies
7. ARM calls Resource Providers sequentially based on dependencies
8. Resource Providers create resources
9. ARM reports success/failure
10. Activity Log records everything

## 1.5 INTERNAL WORKFLOW — What Happens When an Azure VM is Created

Step by step:

1. **Authentication:** User authenticates to Entra ID → receives access token
2. **Authorization:** ARM checks if the user has write permission on the target Resource Group or Subscription
3. **Policy evaluation:** Azure Policy evaluates the deployment — does it comply? (e.g., allowed locations, required tags)
4. **Template validation:** ARM validates the Bicep/ARM template syntax, parameter values, and cross-references
5. **Dependency resolution:** ARM determines creation order (e.g., VNet must exist before NIC, NIC must exist before VM)
6. **Resource provider routing:** ARM routes requests to appropriate providers:
   - `Microsoft.Network` for VNet, Subnet, NIC, NSG
   - `Microsoft.Compute` for VM
   - `Microsoft.Storage` for OS Disk
7. **Provisioning:**
   - Storage Account (hidden, auto-created for managed disks) provisions the disk
   - Network fabric configures the subnet, creates the NIC, applies NSGs
   - Compute fabric provisions the VM on a host
8. **Extension registration:** VM Agent is installed; extensions are configured
9. **Provisioning state:** Resource transitions from `Creating` → `Succeeded` (or `Failed`)
10. **Activity Log:** All operations are recorded
11. **Diagnostic logs:** If configured, resource logs begin flowing

**What happens internally in the compute fabric:**
- Azure's compute orchestrator selects a host based on capacity, availability zone, and host maintenance policies
- The VM is placed on a Hyper-V host (or dedicated host if specified)
- The OS disk is mounted (from managed disk storage)
- The NIC is attached to the VM
- The VM is started (for Linux) or provisioned (for Windows)
- Boot diagnostics captures boot logs to a storage account

## 1.9 PRODUCTION EXAMPLE

**Scenario:** A developer deploys a VM and it fails.

**L3 investigation flow:**
1. Check Activity Log → deployment failed at 14:32 UTC
2. Check error message → "QuotaExceeded — vCPU quota exceeded"
3. Check subscription quotas → 38 vCPUs used / 32 vCPU limit in East US
4. **Root cause:** Quota exceeded, NOT a configuration error
5. **Resolution:** Request quota increase (or deploy to a different region, or delete unused VMs)
6. **Prevention:** Set up budget alerts and capacity monitoring; involve FinOps early

**Why this matters:** A junior engineer might spend hours checking the template, network config, and OS image. An L3 engineer immediately checks quota because they know one of the most common failure causes.

## 1.10 FAILURE SCENARIOS

### Failure 1: Resource Provider Not Registered
- **Symptom:** Deployment fails with "The subscription is not registered for resource provider 'Microsoft.Network'"
- **Root cause:** Subscription was newly created and Microsoft.Network is not auto-registered
- **Fix:** Register the resource provider at subscription level
- **Prevention:** Use Azure Landing Zones or deployment scripts that auto-register common providers

### Failure 2: Quota Exceeded
- **Symptom:** VM creation fails; Activity Log shows QuotaExceeded
- **Root cause:** vCPU quota exhausted in the region
- **Fix:** Request quota increase; deploy to different region or AZ; decommission unused resources
- **Prevention:** Monitor vCPU utilization; request enterprise agreement with higher quotas

### Failure 3: Policy Deny
- **Symptom:** Deployment fails with "PolicyViolation — location East US is not allowed"
- **Root cause:** Azure Policy "Allowed Locations" only permits West US
- **Fix:** Check policy assignment; request exemption or change location; contact policy owner
- **Prevention:** Understand governance constraints before deployment; check effective policies

### Failure 4: Lock Prevents Deletion
- **Symptom:** Cannot delete resource group; error "Resource group 'myRG' has a lock"
- **Root cause:** CanNotDelete lock on the resource group or subscription
- **Fix:** Remove the lock (requires Owner/User Access Admin/authorized role)
- **Prevention:** Document all locks; establish a change control process for lock management

### Failure 5: RG Location Confusion
- **Symptom:** "My VM's resource group is in West US but my VM is in East US — where is my data?"
- **Root cause:** Misunderstanding of metadata location vs resource location
- **Fix:** Check the resource's own location property; check diagnostic settings for actual data location
- **Prevention:** Align RG location with resource location as a standard practice (or document deviations)

## 1.11 TROUBLESHOOTING METHODOLOGY

For any Azure resource deployment or access issue:

**Step 1 — Identity:** Who is performing the action? Are they authenticated? What permissions do they have?

**Step 2 — Authorization:** Does the identity have RBAC permission at the appropriate scope?

**Step 3 — Governance:** Would Azure Policy allow this operation? Are there locks?

**Step 4 — Capacity:** Are there quota or capacity limits that would prevent this?

**Step 5 — Resource Provider:** Is the relevant resource provider registered?

**Step 6 — Configuration:** Is the template/configuration valid? Are references correct?

**Step 7 — Dependencies:** Do prerequisite resources exist? (e.g., VNet exists before VM)

**Step 8 — Platform:** Check Service Health and Resource Health — is this a Microsoft platform issue?

## 1.14 L3 INTERVIEW QUESTIONS

### Basic: "What is a Resource Group?"
**Answer:** A logical container for Azure resources. It does NOT define a security or network boundary. It is a deployment scope, an organizational unit, and a lifecycle management boundary. Resources within an RG can be in different regions. The RG's location is a metadata location, not the location of the resources' data.

### Intermediate: "What is the difference between a subscription and a management group?"
**Answer:** A subscription is a billing and access boundary. A management group is a governance hierarchy above subscriptions. Management groups allow you to apply policy and RBAC to multiple subscriptions simultaneously. Subscriptions belong to management groups; management groups belong to the tenant.

### L3: "A user cannot deploy a VM. The error says 'Deployment failed.' What are the first five things you check?"
**Answer:**
1. Activity Log — what exactly failed and why?
2. Resource Provider registration — is Microsoft.Compute registered?
3. RBAC — does the user have write permission at the scope?
4. Azure Policy — is there a policy violation?
5. Quota — has the user exceeded vCPU quota?

**Why:** These are the top 5 causes of deployment failures. This demonstrates systematic thinking.

### Senior L3: "How would you design a subscription and management group structure for a 200-developer organization?"
**Answer:** Root MG → Contact MG / Sandbox MG / Shared Services MG. Under Production MG → Prod-App1 MG, Prod-App2 MG. Under Non-Prod MG → Dev MG, Test MG, UAT MG. Each application MG has its own subscription(s). Shared Services subscription under Shared Services MG. Sandbox subscription under Sandbox MG with relaxed policies.

### Expert: "What happens internally when ARM processes a deployment?"
**Answer:** ARM authenticates the token via Entra ID, checks RBAC at the deployment scope, evaluates all policy assignments in the scope (with effect and scope), checks for locks, validates the template syntax, resolves resource dependencies, and then sends sequential requests to each resource provider. Each provider handles the actual resource creation in its data plane. ARM reports overall status and logs all operations to the Activity Log. If a deployment fails, ARM stops processing (unless using `--no-wait`), and the partially created resources remain in a `Creating` or `Failed` state.

### Scenario: "What would you do if a deployment consistently fails but the configuration looks correct?"
**Answer:** I would check (in order): Activity Log for the specific error, resource provider registration, policy compliance status, subscription quotas, resource locks, and service health. Misconfiguration is rarely the issue when "everything looks right" — it's usually quota, policy, provider registration, or platform.

### Tricky: "A resource group has a ReadOnly lock. Can you still update resources inside it?"
**Common wrong answer:** "No, ReadOnly means no changes."
**Correct answer:** No. A ReadOnly lock at the resource group level prevents ALL write operations on ALL resources within that resource group, even if the individual resource has no lock. This is a common point of confusion — some engineers think locks only apply if they're on the specific resource, but locks are inherited.

**Why the wrong answer is wrong:** ReadOnly locks are absolute at their scope. They override individual resource settings. This is by design — locks are meant to protect resources from ANY modification, including by resource owners.

**Likely follow-up:** "How do you delete a resource that has a CanNotDelete lock inherited from its resource group?" Answer: You must either remove the lock (requires authorization), or move the resource to a resource group without the lock and then delete it. You cannot delete a locked resource.

## 1.15 SCENARIO-BASED QUESTIONS

### Scenario 1: "You deploy a VM using an ARM template. It fails with 'NotFound' on a subnet reference. The subnet exists. What's wrong?"
**Investigation chain:**
- The subnet resource ID in the template might reference a different VNet or different subscription
- The template might use a name reference that doesn't match
- The deployment scope might not have access to the resource group containing the subnet
- **Common cause:** Cross-RG or cross-VNet references not properly specified with full resource IDs

### Scenario 2: "Deployment succeeds but the VM is not reachable. What do you check first?"
**Investigation chain:**
- Is it a platform issue? (Check Service Health / Resource Health)
- Is it a network issue? (Check NSG, route table, public IP, DNS)
- Is it an OS issue? (Check boot diagnostics, RDP/SSH access)
- L3 approach: Follow the packet path from source to destination checking each hop

### Scenario 3: "Your manager says 'why can't I create a resource in this subscription even though I'm an Owner?'"
**Investigation chain:**
- Check if they're in the right tenant (Azure portal can show multiple tenants)
- Check Azure Policy (Azure Policy Deny can block even Owners)
- Check for locks (CanNotDelete on subscription prevents creation of some resources... actually, CanNotDelete prevents DELETION, not creation; but Check if subscription has a Deny Assignment)
- Check RBAC: are they actually an Owner on the subscription? Check effective permissions with `What-If` or Access Review
- Check resource provider registration

## 1.16 KNOWLEDGE TEST

1. **What is the difference between a subscription's location and a resource's location?**
   Subscriptions don't have a "location" per se. Resource Groups have a location (metadata location). Resources have a location (where they physically operate). These can be different.

2. **Can a resource exist without a resource group?**
   No. Every resource must be in exactly one resource group.

3. **Can a resource group contain resources from multiple subscriptions?**
   No. A resource group belongs to one subscription and can only contain resources from that subscription.

4. **What happens if a resource provider is not registered?**
   You cannot create, update, or delete resources of that type. Existing resources may continue to function but you cannot manage them through ARM.

5. **True or False: The Azure Resource Manager is responsible for routing VM network traffic.**
   False. ARM is the control plane (management). VM network traffic goes through the network fabric (data plane), not through ARM.

6. **What is the maximum depth of a management group hierarchy?**
   6 levels (including root).

7. **Can a subscription belong to multiple management groups?**
   No. A subscription can have only one parent management group.

8. **What is the difference between Resource ID and Resource Name?**
   Resource Name is unique within its resource group. Resource ID is globally unique and contains the full path (subscription, RG, provider, type, name).
